---
title: Build a code reviewer
description: Let one reviewer create the review agent and verifier a patch needs.
---

A useful code review has three responsibilities:

- The reviewer reads the requirements, diff, surrounding code, and tests. It
  decides which risks deserve deeper review.
- A reviewer chosen for the affected risk surface investigates it and returns
  candidate defects with evidence.
- A verifier tries to disprove each candidate against the code and
  requirements.

Triage is a responsibility of the reviewer, not necessarily another agent. A
candidate becomes a published finding only after verification.

## Define the reviewer

This reviewer has repository tools and `eval`:

```clojure
(defn code-reviewer [repo]
  (let [repo-tools
        (->> (k/local-tools
              {:cwd repo
               :needs-approval {:read :never
                                :search :never
                                :bash :always}})
             (filterv #(contains? #{"read" "search" "bash"} (:name %))))]
    (k/agent
     {:name "reviewer"
      :model "gpt-5.6"
      :instructions
      "Review the current patch as a maintainer.

       Read the repository guidance, diff, affected code, callers, and relevant
       tests. Decide what kind of review the change needs and use eval to
       author and run that reviewer. Pass its complete candidate report to a
       separately authored verifier.

       Publish only defects introduced by the patch that the verifier confirms.
       For each finding, include severity, path and line, a concrete failure
       scenario, evidence, and the smallest reasonable fix. Do not report style,
       pre-existing problems, or speculation."
      :tools (conj repo-tools k/eval)})))
```

The application supplies access to the repository and the review standard. It
does not predefine a security reviewer or verifier.

After reading an authorization-sensitive patch, the model can use eval to
construct those agents. The eval tool description teaches it the `agent`,
`run!`, `output`, and `input` bindings.

Constructed agents do not inherit the reviewer's tools. If another reviewer needs
repository access, the evaluated expression must give it the available tools
explicitly.

## Run the review

```clojure
(k/run! (code-reviewer "/workspace/project")
        "Review the current working-tree diff."
        {:approval approve-review-command
         :on-event (k/monitor {:display :tree})})
```

The reviewer may run a narrow test when it helps prove or disprove a finding.
The approval handler decides whether a proposed command may execute.

## Run the bundled example

The repository includes a smaller example that does not require another
checkout:

```bash
OPENAI_API_KEY=... clojure -M:examples review
```

Its input describes a customer export endpoint with this requirement:

```text
Only users with the :admin role may export customer data.
Other authenticated users must receive 403.
```

The patch calls `auth/require-user`, which authenticates the caller but does not
check roles. The reviewer should recognize the authorization boundary, author a
`security-reviewer`, and then author a `verifier`.

```text
run! reviewer
└─ reviewer
   └─ eval
      ├─ security-reviewer
      └─ verifier
```

The security reviewer should identify the missing role check. The verifier
should confirm it from the stated behavior and reject unsupported candidates.
The reviewer then publishes the final finding.

## Inspect what the model wrote

At a REPL:

```clojure
(require '[karcarthy :as k])
(load-file "examples/review/main.clj")

(def result
  (example.review/run-review!
   example.review/default-change))
```

The eval events retain the model-authored expression and its macroexpansion:

```clojure
(->> (k/events result)
     (filter #(= :eval/expanded (:type %)))
     (map #(select-keys % [:agent :depth :expression :expansion])))
```

Inspect the participating agents separately:

```clojure
(->> (k/events result)
     (filter #(= :agent/started (:type %)))
     (map (juxt :agent :parent-id :depth)))
```

The first query shows what the reviewer authored. The second shows what the
harness ran.

## Judge the result

For this example, check:

- Did the reviewer choose security review because the patch crosses an
  authorization boundary?
- Did the security reviewer identify the missing admin-role check?
- Did the verifier test the candidate against the supplied requirement and
  existing behavior?
- Did the final answer omit rejected or unsupported claims?
- How many model calls, tokens, and eval attempts did the run use?

The final review is model output. The diff, test results, verifier verdicts, and
retained events are the evidence for assessing it.
