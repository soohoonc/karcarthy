---
title: Agent orchestration
description: Decide who defines the agents and when.
---

Another agent can enter a program in three ways:

1. The application makes it available through `:agents`.
2. Application code calls it with `run!`.
3. A model authors it inside `eval` after reading the input.

These are ordinary agent values and ordinary Clojure calls. karcarthy does not
turn them into workflow nodes.

## Make an agent available

Use `:agents` when the application knows the possible agents but wants the
model to decide whether to call one:

```clojure
(k/defagent verifier
  {:description "Check a proposed code-review finding against the supplied code."
   :model "gpt-5.6"
   :instructions
   "Try to disprove the finding. Return CONFIRMED, REJECTED, or NEEDS CONTEXT."})

(k/defagent reviewer
  {:model "gpt-5.6"
   :instructions
   "Review the patch. Ask the verifier to check every candidate finding."
   :agents [verifier]})
```

The verifier is already defined before `reviewer` runs. The model sees it as a
callable capability, chooses whether to call it, and supplies its input. The
verifier starts a fresh model conversation and returns its output to the
reviewer.

## Call agents from application code

When the participants and order are already known, write the coordination as a
normal function:

```clojure
(defn review-change [change]
  (let [candidates
        (k/output (k/run! security-reviewer change))]
    (k/output
     (k/run! verifier
             (str change "\n\nCandidate findings:\n" candidates)))))
```

Use `let`, `if`, `case`, functions, macros, collections, `future`, and `deref`
normally. There is no karcarthy workflow API to learn.

Calls made outside an active run establish separate runs. Calls made from a
tool or evaluated expression participate in that active run.

## Let the model author the program

Use `k/eval` when the input should determine which agents exist:

```clojure
(k/defagent reviewer
  {:model "gpt-5.6"
   :instructions
   "Review this pull request. Decide what kind of review the patch needs,
    author and run that reviewer with eval, then pass its candidates to a
    verifier."
   :tools [k/eval]})
```

After seeing a change to an administrative export route, the reviewer can send
this code to `eval`:

```clojure
(let [security-reviewer
      (agent
       {:name "security-reviewer"
        :model "gpt-5.6"
        :instructions
        "Review authentication, authorization, and sensitive-data access.
         Return only candidate vulnerabilities introduced by the patch."})
      candidates (output (run! security-reviewer input))
      verifier
      (agent
       {:name "verifier"
        :model "gpt-5.6"
        :instructions
        "Try to disprove each candidate against the requirements and code."})]
  (output
   (run! verifier
         (str input "\n\nCandidate findings:\n" candidates))))
```

The reviewer wrote both agent definitions. They were not supplied through
`:agents`. The `agent`, `run!`, and `output` symbols are available because the
eval tool installs them in the evaluation namespace. `input` is the original
review request.

The eval tool description explains this API to the model. It also lists any
tools and agents that the application did supply, so evaluated code can use
those values by name.

## Pass data explicitly

One agent does not inherit another agent's conversation. Pass the data it
needs:

```clojure
(let [candidates (output (run! security-reviewer input))]
  (output
   (run! verifier
         (str input "\n\nCandidate findings:\n" candidates))))
```

This is why the verifier receives both the original change and the candidate
report.

## Run work concurrently

Use Clojure futures when calls are independent:

```clojure
(let [jobs (mapv #(future (run! % input)) reviewers)]
  (mapv #(output @%) jobs))
```

Dynamic run bindings flow into the futures. All calls share the run ID, limits,
usage, events, cancellation, approvals, context, and executor.

## Choose the boundary

| Approach | Who defines the agents? | When? |
| --- | --- | --- |
| `:agents` | The application | Before the run |
| Application code | The application | Before the input is handled |
| `k/eval` | The model | After reading the input |

These approaches can be combined. An eval-enabled reviewer may use a
predefined repository tool, construct a new reviewer, and call both in one
expression.

## Trust

Eval runs full-trust Clojure in the current JVM. The one-expression rule is a
protocol boundary, not a sandbox. Isolate the process when model-authored code
should not have the process's filesystem, network, credentials, or classpath
authority.

See [Eval](/docs/reference/eval) for the exact tool and evaluation behavior.
